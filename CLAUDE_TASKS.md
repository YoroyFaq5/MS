# Задачи для Claude: сезонный рейтинг, GG и «Стол года»

Работай в текущем репозитории MafiaTracker. Сначала изучи существующую реализацию, затем внеси изменения и проверь их тестами. Не меняй постороннюю функциональность и не трогай уже имеющиеся пользовательские изменения в рабочем дереве.

## 1. Ограничение мест 1–5 сезонного рейтинга

В сезонном рейтинге места с 1-го по 5-е может занимать только игрок, сыгравший не менее 8 завершённых рейтинговых игр в этом сезоне.

Требования:

- Источником количества игр должна оставаться каноническая сезонная выборка: завершённые рейтинговые игры с `Game.season_id == season_id`.
- Игроки с 8 и более играми ранжируются по текущему `season_rating` и занимают доступные места 1–5.
- Игрок с 0–7 играми не должен получить ранг 1–5 независимо от количества очков. Такие игроки остаются видимыми в таблице, но их ранг начинается с 6.
- Если подходящих игроков меньше пяти, не заполняй свободные места 1–5 игроками с недостаточным числом игр: после подходящих игроков у следующего неподходящего игрока должен быть ранг 6.
- После места 5 все игроки ранжируются по текущему `season_rating` независимо от числа игр; порядок при равенстве должен быть детерминированным.
- Правило должно применяться централизованно в `SeasonRatingEngine`, чтобы одинаково работать в UI, API, закрытии сезона, тай-брейке, сезонных наградах, достижениях и квалификации в «Стол года».
- Закрытие сезона и ручной тай-брейк не должны позволять выбрать победителем игрока с менее чем 8 играми.
- Добавь понятное отображение/пояснение в сезонной таблице для игроков, которые ещё не выполнили минимум 8 игр.

## 2. Вес GG только для будущих сезонов

Текущий и исторические сезоны должны навсегда сохранить формулу `GG * 0.2`. Начиная со следующего созданного сезона, вес GG должен быть `0.1`.

Реализуй это как версионированное правило сезона, а не как замену глобальной константы:

- Добавь к модели `Season` сохраняемый в БД вес GG (например, `gg_weight`).
- Подготовь Alembic-миграцию: всем уже существующим сезонам присвоить `0.2`; колонка должна быть `NOT NULL` с безопасным значением для старых записей.
- `SeasonService.ensure_year_exists()` должен создавать новые сезоны с весом `0.1`.
- `SeasonRatingEngine` должен использовать вес конкретного сезона. Исторический пересчёт старого сезона обязан дать прежний результат.
- Обнови тексты формулы в docstring, README и интерфейсе, чтобы они не утверждали, что вес всегда равен 0.2.
- Не определяй «следующий сезон» через текущую дату при каждом расчёте: коэффициент должен фиксироваться в записи сезона при его создании.

## 3. Проверка и исправление регистрации в турнир «Стол года»

Проведи полный аудит механики в `SeasonService.compute_year_qualifiers()`, `_sync_year_tournament_participants()`, `_register_winner_in_year_tournament()` и `create_year_tournament()`.

Ожидаемые правила:

- Учитываются только завершённые сезоны без нерешённого тай-брейка.
- Сезоны обрабатываются по номеру; более ранний сезон имеет приоритет.
- Из сезонов 1–5 проходят по два уникальных игрока, из сезона 6 — один.
- Кандидат на квалификацию обязан быть активным и, с учётом задачи 1, реально занимать место 1–5 и иметь не менее 8 игр в сезоне.
- Один игрок может быть зарегистрирован в «Столе года» только один раз. Если он уже квалифицировался в более раннем сезоне, берётся следующий допустимый игрок текущего сезона.
- Повторный запуск синхронизации идемпотентен.
- Итоговый состав должен точно соответствовать актуальному вычисленному набору квалификантов. Текущая add-only логика оставляет устаревших/лишних участников; исправь это безопасно для турнира в статусе `pending`. Для уже активного или завершённого «Стола года» не меняй состав молча: верни ясное предупреждение/ошибку и не порть данные.
- Не удаляй вручную добавленного участника без явного способа отличить его от автоматически квалифицированного. Если модели не хватает происхождения регистрации, добавь явное поле/связь или другую надёжную схему происхождения и миграцию.
- Проверь согласованность статусов: обычная регистрация сейчас разрешена в активный турнир, а удаление запрещено; удаление также разрешено для завершённого турнира. Приведи правила к безопасной и симметричной модели, не ломая необходимый сценарий регистрации «Стола года».
- Проверь закрытие сезонов не по порядку, повторное закрытие/пересчёт, смену результатов, неактивного игрока, дубли, недостаток допустимых кандидатов и уже существующий турнир.

## 4. Исправление нелогичных переходов и контекстной навигации

Проведи аудит пользовательских переходов, прежде всего в сценариях создания, просмотра и завершения игр внутри обычного или серийного турнира. Исправь следующие подтверждённые проблемы, не перестраивая дизайн приложения целиком.

### Контекстный возврат из игры

- Сейчас ссылка «Назад»/«Все игры» на странице игры всегда ведёт в общий список игр.
- Для обычной турнирной игры возврат должен вести на страницу соответствующего турнира или его списка игр — выбери один последовательный вариант для всего сценария.
- Для игры конкретного вечера серийного турнира возврат должен вести на страницу этого вечера, а не на турнир-обёртку и не в общий список игр.
- Для игры вне турнира возврат по-прежнему ведёт в общий список игр.
- Это поведение должно одинаково работать после просмотра, сохранения, завершения, редактирования и исправления состава игры.

### Сохранение контекста при создании игры

- Страница создания игры, открытая из турнира или вечера серии, не должна терять источник перехода при ошибке валидации, отмене или успешном создании.
- Введи безопасный централизованный механизм возврата, например строго валидируемый `next`/`return_to` или серверное определение контекста по `tournament_id` и `stage_id`.
- Не допускай open redirect: нельзя перенаправлять на произвольный внешний URL или непроверенный адрес из запроса.
- Приоритет возврата: конкретный вечер серии → обычный турнир/его игры → общий список игр.

### Ссылки серийных турниров

- На общей странице турниров карточки серийного турнира не должны отправлять пользователя в интерфейс обычного турнира для действий «Открыть», «Рейтинг» и «Этапы».
- Если для турнира существует `SeriesTournament`, веди непосредственно на соответствующие страницы серийного турнира и его рейтинга.
- В интерфейсе турнира-обёртки оставь ясный переход в серийный турнир, но не показывай действия обычного турнира, которые не имеют смысла для серии или могут привести к ошибочной операции.
- Проверь хлебные крошки/кнопки «Назад» между списком турниров, серийным турниром, вечером серии, игрой и рейтингом: пользователь должен возвращаться на один логический уровень вверх.

### Единая логика изменения состава турнира

- Сейчас регистрация участника разрешена для активного турнира и запрещена только для завершённого, а удаление запрещено для активного, но фактически разрешено для завершённого. Устрани эту асимметрию.
- По умолчанию состав вручную изменяется только у турнира `pending`.
- Для `active` и `finished` запрещай и добавление, и удаление через обычные методы с понятным сообщением.
- Если приложению действительно необходима замена игрока в активном турнире, она должна быть отдельной явно названной операцией с проверкой уже сыгранных игр, команд, посадок и рейтинга, а не побочным эффектом обычной регистрации.
- Автоматическая синхронизация будущего «Стола года» должна подчиняться отдельным правилам из задачи 3 и работать только пока он `pending`.

### Общий механизм возврата

- Убери дублирующиеся и противоречивые решения о редиректах там, где это разумно: создай небольшой серверный helper/DTO, определяющий канонический URL возврата для игры и турнирного контекста.
- Не передавай бизнес-решения в JavaScript или шаблоны, если контекст надёжнее определяется сервером.
- После POST используй Post/Redirect/Get и сохраняй flash-сообщения.
- Не ломай прямые ссылки и существующие имена Flask endpoints без необходимости.

## Тесты и результат

Добавь автоматические тесты как минимум на:

1. Игрок с высоким рейтингом и 7 играми не попадает в топ-5; игрок с 8 играми попадает.
2. При менее чем пяти подходящих игроках неподходящий игрок получает ранг 6, а не свободное место 1–5.
3. Старый сезон использует GG 0.2, новый — 0.1; исторический результат не меняется.
4. Квалификация «Стола года» соблюдает 2+2+2+2+2+1, уникальность, минимум 8 игр и ограничение мест 1–5.
5. Повторная синхронизация не создаёт дублей и удаляет/заменяет только устаревшие автоматические регистрации в `pending`-турнире.
6. Активный/завершённый «Стол года» не получает скрытых изменений состава.
7. Возврат из обычной турнирной игры ведёт в её турнир, из игры серии — в конкретный вечер, из обычной игры — в список игр.
8. Создание игры сохраняет тот же контекст при успехе и ошибке; внешний или некорректный `next` игнорируется.
9. Карточки серийных турниров ведут в серийный интерфейс и не предлагают несовместимые действия обычного турнира.
10. Добавление и удаление участников разрешено только для `pending`; для `active` и `finished` оба действия отклоняются без изменения данных.

После реализации запусти доступные тесты и статические проверки. В отчёте перечисли изменённые файлы, миграцию, покрытые сценарии и оставшиеся риски. Не делай коммит без отдельной команды.
